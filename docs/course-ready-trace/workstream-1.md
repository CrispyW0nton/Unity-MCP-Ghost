## Required gaps: precise evidence and minimum next gates

### G1 — repair_apply_edits still hides nested failures

Source-confirmed false-success paths, not a general criticism of the central adapter. A concurrent source edit can make the dry-run script.apply_edits return an expected-hash error; `CS:2486–2500` nevertheless returns top-level `ok:true`. On the apply path a `script.transaction_complete` soft failure is stored in steps but omitted from final success at `:2640`. The adapter only inspects top-level fields and the conventional state object, so these nested results remain MCP successes. This directly reopens P0 #2 for this public workflow.

Minimum gate: add real MCP-route tests for failed dry-run preview and failed cleanup, assert `isError:true`, preserved producer error/receipt and no later mutation after failed preview; then make the orchestration propagate those results. Existing generic soft-failure tests are not substitutes.

### G2 — real Test Runner infrastructure failures do not enter failed state

`HandleTestsRun` registers a running record at `BR/CommandRegistry.cs:573`, then executes at :574 without a catch that terminalizes the record. If Execute throws, CommandRegistry's outer catch returns an error but the test record remains running. Independently, `GhostTestRunCallbacks` implements only ICallbacks. The pinned Test Framework 1.1.33 has a distinct IErrorCallbacks.OnError path for build/prebuild failures (`UTF/Api/IErrorCallbacks.cs:6` and `CallbacksDelegator.cs:67–70`), so that failure path never updates this callback's StateJson.

Minimum gate: exercise a thrown start and a real prebuild/infrastructure callback; assert durable terminal failure and typed MCP operation error, then fix both update paths. The literal-string classification test cannot close this gate.

### G3 — test timeouts leave the underlying run active

`tests_run` exposes no run timeout (`CS:2359`), the Unity handler stores only callbacks.StateJson, and OperationStore has no test execution deadline. `pollOperation:315–328` returns the latest running state when its wait expires. The repairs interpret non-success as test failure and start source restoration without stopping/settling the actual test job. This contradicts the explicit WS1 requirement that timeout end in failed/cancelled state and undermines safe required-test rollback.

Minimum gate: controlled running test that crosses the configured wait limit; assert a terminal failed/timed-out receipt, cancellation/settlement of the test before source restoration, and no later callback turning timeout green. Test this separately from an injected response whose status already equals timeout.

### G4 — cancellation cannot reach the pinned Test Runner API

`CancelTestRun:3154` searches `BindingFlags.Instance | BindingFlags.Public` for a zero-argument method. Source inspection of the actually resolved `com.unity.test-framework@1.1.33/UnityEditor.TestRunner/Api/TestRunnerApi.cs` found no CancelTestRun method. Hence this supported environment follows the explicit throw at :3157; OperationStore catches it and produces outcomeUnknown. This is honest uncertainty but is not the required controlled-environment cancellation implementation. The record advertises cancellationSupported because a callback exists.

Minimum gate: implement/resolve cancellation against the actual supported runner interface, then cancel a real active run and assert terminal cancellation plus no ongoing test actions. If the underlying API genuinely cannot cancel, expose that limitation truthfully while completing the mandated local cancellation behavior through an explicitly supported execution path. No new public tool is required by this finding.

### G5 — older repair_apply_edits can skip restoration or destroy recovery before verification

Any exception after confirmed apply and before the ordinary rollback branch reaches the catch at `CS:2660`, which only returns failureResponse; it performs no restoration and returns no retained backup evidence. For example, tests.run can throw after a successful write and compile. Within the normal rollback branch, `rollbackCompile.ok` and the computed `byteIdentical` are not preconditions for the two backup cleanup calls at :2596 and :2602. Even when restore compilation times out or the read-back hash differs, it deletes the original and rollback backups, then reports mode `rolled-back`.

Minimum gate: port the recovery guarantees already directly tested for repair_loop_run into this separately public path (sharing a scoped helper is an implementation choice). Add a throwing required-test start, unsuccessful restoration compile, hash mismatch and cleanup failure; require restoration or retained recovery evidence, never unconditional cleanup/unverified restoration. Also ensure explicit rollbackOnFailure options do not allow a required non-green test to retain an unverified repair under the milestone contract. This finding does not request deletion or renaming of existing functionality.

### G6 — public compile waiting can return success after its deadline and cannot observe MCP cancellation

`waitForUnityCompile` tests elapsed time at loop entry (`CS:339`) and immediately returns a successful state after awaited compile.status_get (`:350`). A read admitted before the deadline and returned after it is therefore accepted as success. No remaining-deadline timeout is passed into that read. It also trusts `status:success` without requiring matching returned generation/observed/completed metadata. The public handler wrapper ignores the SDK extra argument entirely (`CS:197`; ToolHandler accepts only args), so cancellation is not passed to this loop. Its broad catch suppresses cancellation-like request errors until a subsequent response or the outer timeout.

The separately hardened ScenarioJobManager compiler loop and its after-read deadline/cancel tests do not apply to compile_wait, script_validate or the two repair workflows, all of which call this helper.

Minimum gate: deterministic real MCP-route tests of a held status read returned at/after deadline, cancellation during a read, and invalid completion evidence; assert typed MCP failure and no subsequent diagnostic/test/mutation work after cancellation. Share or bring this path up to the already required exact-generation observation contract. This is source-confirmed control flow, not a timing reproduction in this audit.

### G7 — repair_apply_edits still counts historical Console compiler diagnostics

Although compiler generation filtering is correct, `CS:2540` requests console.diagnostics_get without a boundary or generation. `BR/CommandRegistry.cs:134` forwards to `ConsoleLogBuffer.Diagnostics:45`, whose query sets severity/file/limit but no boundary or generation against the persistent buffer. `CS:2559` takes the maximum of those historical Console errors and validation diagnostics, then `:2564` rolls back. A prior compiler error for the same script can therefore reject a presently clean exact generation. The new repair loop does not use this historical Console branch, but the older repair API remains public. This is the original P0 #3 failure pattern in an adjacent workflow.

Minimum gate: seed a prior same-script compiler Console error, then report a clean observed completed generation for the current apply; assert no historical-error rollback. Use the current generation/boundary for any required Console checks.

## Evidence gaps, not demonstrated runtime failures

- **E1 — strict JSON edge coverage:** current tests prove the listed basic malformed cases, nested duplicate keys and a limited escape round trip. They do not prove lexical rejection/round-trip behavior for comments, single quotes, trailing commas, malformed control/Unicode escapes and numeric extremes. `CommentHandling.Ignore` is visible source behavior; this report does not claim an executed exploit or authentication bypass. Minimum next gate is a bounded parser-edge test table, especially the inputs the real configured parser accepts beyond strict JSON, before calling P0 #15 fully verified.
- **E2 — callback-to-MCP failed test details and rollback:** TestFinished/RunFinished and persistence code exist, but no direct test invokes the callbacks and asserts failed-test details, failed durable state, MCP isError and subsequent repair rollback. The fixed classifier and mocked repair tests provide complementary partial evidence only. Minimum next gate is a real failing fixture test through the bridge with these end-to-end assertions.
- **E3 — actual import/no-op generation and monotonic reload evidence:** mutation handlers attach generation/hash; buffer unit tests manually invoke begin/complete. No assertion proves a same-content ForceUpdate or already-current script_validate observes/completes a generation, nor monotonic generation after actual reload. Source inspection establishes the missing explicit import/no-op path, but not whether Unity happens to compile every such call in this environment. Minimum gate: a bounded real fixture test for changed source, unchanged source, validation-only and reload, asserting generation ordering, observed/completed status, source hash and clean diagnostics. Fix only failing cases established by that test.
- **E4 — composite repair request identity:** direct script requests have strong ID/dedup tests. Whole repair invocations accept outer request identity but child requests use separate/generated identities, and the wrapper rewrites envelope requestId after a lost apply. The existing unknown-apply tests omit outer identity. Minimum gate: supply an outer ID/idempotency key, lose a nested apply response, then retry/reconcile using the public receipt; assert unambiguous outer/child IDs and no unintended repeated mutation. This report does not assume that different outer/child IDs alone are a defect.
