## Required gaps and minimum closure work

These are acceptance gaps in the frozen requirements, not a proposed general improvement program. No test execution or fault reproduction was performed for the source findings below.

### G1 — unresolved script backups can be removed, and standalone mutation lifecycle is incomplete (W2.9–W2.10)

`ScriptFileTransaction.TrimBackups` sorts ordinary groups by last-write time and deletes all after 50. No persisted owner, generation, required-test outcome, or pending restoration participates in that choice. `BeginBackupRetentionLease` is an in-memory counter; only the synchronous batch acquires it. The existing 51-to-50 test demonstrates the current count policy, not validation-safe retention. Scenario `ApplySources` saves references to these ordinary backups, so its durable transaction record does not make its referenced files exempt. The public script handlers return after an import request and do not later observe compiler/test failure or cancellation to finalize/restore their own transaction.

Minimum closure: retain durable pending transaction/backup ownership until validation or verified restoration finishes, with admission/storage bounds rather than pruning unresolved recovery material. Tie the requested standalone mutation semantics to that finalization path. Add direct tests for an unresolved oldest backup surviving 51 newer writes and reload, and per-operation compile/test failure, timeout and cancellation restoring byte-identical source/absence and relevant metadata. Physically blocked restoration must retain recoverable bytes and report unknown/incomplete, as allowed by the governing amendment.

### G2 — batch does not validate every item before mutation (W2.13)

The preflight loop adds `{ok:true,readOnly:true}` and continues for every read-only policy. Nested schemas are not resolved on the TypeScript side either. An invalid later `gameobject.get`/`operation.get` parameter set can therefore be discovered only after a preceding valid mutation executes. Existing unknown-method tests do not reach this branch.

Minimum closure: perform non-mutating argument validation for every resolved method before beginning execution, including read-only methods. Add a direct registry regression with valid first mutation and invalid later read-only parameters proving the first mutation never occurs.

### G3 — failed executing-item recovery is not included in batch outcome (W2.19–W2.20)

`HandleBatchExecute` registers rollback records only for `itemOk`. `ScriptFileTransaction` can return `ok:false` with `error.restorationStatus` equal to `incomplete` or `unknown` after changing bytes. This receipt stays inside the item but is absent from `RollbackBatch`. A required item yields top-level failure with a potentially misleading `rollback.ok:true`; an optional item does not set `requiredFailure` at all and can yield top-level `ok:true`. The existing failed-rollback test injects failure during compensation of a previously successful item, so it does not cover this branch.

Minimum closure: aggregate failed-item restoration evidence and make incomplete/unknown compensation fail the batch regardless of the item's optional/required setting; preserve all recovery receipts. Add paired direct registry tests for required and optional partial script failure and assert top-level failure, accurate rollback outcome, retained backup bytes and continued safe compensation.

### G4 — HTTP/WS cancellation does not reach a queued mutation (W2.25)

HTTP abort only cancels Node fetch; WebSocket cancellation only removes Node pending state. `DispatchDurably` receives no cancellation argument and its queued action consults only the original absolute deadline. A request cancelled before its deadline while Unity is busy can still execute later. `outcomeUnknown` is honest client reporting but does not implement the separately required cancel-before-execution opportunity.

Minimum closure: use an authenticated cancellation/request-state mechanism consulted atomically at queued admission/execution, preserving unknown outcome when execution has already begun. Add actual HTTP and WS queue-boundary tests cancelling a held mutation before drain, plus race-after-admission tests proving no implicit replay and truthful uncertainty.

### G5 — durable generic operation records do not establish reload-resilient jobs (W2.32)

Persisted completed receipts are implemented. However, nonterminal package/compile/test operations depend on closures in static `OperationStore.Operations`. On loss of that dictionary, `Refresh/List` permanently record `outcomeUnknown`. `RunningOperationBecomesOutcomeUnknownAfterDomainReloadSimulation` asserts precisely this fallback. That is safe against false success but does not prove the required controlled-environment job lifecycle survives a normal domain reload; a normal reload is not permanently unavailable storage/Editor under the amendment.

Minimum closure: establish and directly test resumable/reconcilable state for required reload-crossing jobs (especially compile/tests and course-loop dependencies), or demonstrate their exact completed result remains observable through reload with the current subsystem callbacks. Use a real domain-reload gate as well as store tests. Keep honest unknown outcomes for the impossible fault conditions explicitly allowed by the governing document. Do not infer generic job continuation from scenario mocks or completed-record reload simulation.

### G6 — queue storage and housekeeping bounds/cleanup are incomplete (W2.34–W2.35)

### G7 — exceptional transport cleanup/completion paths are not closed (W2.35)

`UnityClient.requestViaQueue` writes a unique `.tmp` and renames it without an owned-temp cleanup `finally`; rename failure retains the temporary file. On Unity, `DispatchDurably`'s `complete` evaluates `RequestExecutionStore.Complete` before `TrySetResult`. A persistence failure throws; dispatcher `OnError` calls the same failing completion again, so the pending `TaskCompletionSource` may never complete. HTTP concurrency remains held while its caller awaits it. `WriteHttpResponse/WriteStatusResponse` also have no per-response output deadline/finally-close; they use only the service-lifetime token. The separate MCP-facing `streamableHttp.ts` fixes do not cover this Node-to-Unity bridge.

Minimum closure: clean owned publication temporaries on failure, guarantee a bounded visible failure completion when durable result publication fails without replaying mutation, and directly verify bounded response cleanup. Add fault-injection tests at queue rename and durable result persistence, and a stalled response writer test. Do not hide retained recovery evidence as a successful cleanup.

### G8 — screenshot exceptional cleanup evidence is missing (W2.38)

`LoadScreenshotTexture` constructs a Texture2D and calls `LoadImage`. It destroys on false return and header mismatch, but has no local exception cleanup. Capture's existing `finally` is source evidence but lacks direct allocation/render/encode-failure assertions.

Minimum closure: give the decoder local ownership with destruction on every unsuccessful return/throw; directly fault-test decode and capture allocation/encode failures, including restoration of camera target/active render target and object release.

### G9 — containment policy is not applied to all scoped filesystem paths (W2.41)

The policy itself has direct junction tests. Screenshot capture and baseline cleanup bypass it for their computed storage directory and per-file paths; a junction at `Library/UnityMcpGhost/screenshots` can redirect writes or deletion outside the selected project. Minimum closure: validate computed storage roots and each actual read/write/delete target through the same containment/reparse policy before I/O. Add Windows junction regressions for screenshot write/cleanup and representative durable-state/queue publication proving external sentinel bytes remain untouched.

### G10 — operation listing silently truncates (W2.42)

`OperationStore.List` takes 1,000 entries and does not include truncation or a continuation mechanism.
